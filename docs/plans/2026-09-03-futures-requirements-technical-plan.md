# 国内期货功能需求与技术方案

> 状态：待确认方案（尚未实施）
>
> 日期：2026-09-03
>
> 适用项目：股票期货实时监控助手 v2
>
> 依据：当前源码、`STATUS.md`、两轮代码审查 handoff，以及交易所/AKShare 当前公开资料
>
> 重要边界：本文是独立的期货需求与实施方案，不代表当前代码已经具备这些能力。

## 1. 背景与现状

项目名称和早期 `SPEC.md` 都宣称支持股票与期货，但当前实现只有不完整的期货实时报价骨架：

- `src/js/app.js` 仅识别带 `nf` 前缀的输入，普通合约代码如 `rb2510` 无法直接添加。
- `src/js/api.js` 通过新浪请求期货实时行情，但当前 URL 缺少实际接口所需的 `nf_` 形式。
- `src/js/parser.js` 的返回变量正则也不接受 `nf_`，因此真实期货报价链路当前不可用；现有测试使用了错误的 mock 契约，未发现该问题。
- 股票分时、K 线和服务端共享缓存只接受 A 股代码，没有期货图表数据源。
- `marketSession.js` 只表达 A 股日盘时段，不能处理商品期货的 09:00 开盘、10:15 休市、夜盘、跨自然日和中金所差异。
- 语音和提醒对象虽然接受 `type: 'future'`，但没有建立在可用、可验证的期货行情之上。

因此，当前产品只能称为“计划支持期货”，不能称为“已经支持期货”。完整实现必须同时补齐标识、合约目录、实时报价、图表、交易时段、缓存和测试，不能只修复一个新浪 URL。

## 2. 产品目标

在不破坏现有 A 股功能的前提下，为中国境内期货建立可靠的行情监控能力：

1. 用户可输入并监控具体期货合约、主力合约和连续合约。
2. 监控列表在实际交易时段持续刷新最新价、涨跌、成交量和持仓量。
3. 选中期货后，页面继续遵守既定布局：左侧分时、右侧 K 线同时显示，不改为 tab 单画布。
4. 图表覆盖夜盘并正确归属交易日，实时价格能同步更新分时末点和当前 K 柱。
5. 语音播报、阈值提醒、持久化和错误提示对期货可用。
6. 数据源异常时可降级、可识别陈旧数据，不用空数据覆盖最后一次成功数据。

## 3. 范围与非范围

### 3.1 首个完整版本必须包含

- 境内六家期货交易场所的期货合约：上期所、上期能源、大商所、郑商所、广期所、中金所。
- 具体合约，例如 `RB2510`、`IF2603`。
- 主力/连续序列，例如 `RB0`、`IF0`，并明确标识“连续序列不可直接交易”。
- 商品期货和金融期货实时报价。
- 当个交易日分时，以及 1/5/15/30/60 分钟 K 线。
- 日/周/月 K 线；具体合约和连续合约分别缓存，严禁混用。
- 最新价、昨结、涨跌额、涨跌幅、今开、最高、最低、买一、卖一、成交量、持仓量、动态结算价（数据源提供时）。
- 日盘、夜盘、跨午夜、节假日前后无夜盘等会话判断。
- 监控列表、语音播报、阈值提醒、浏览器通知、刷新状态和持久化。
- 左分时、右 K 线双图常驻；桌面端并排，窄屏按现有响应式规则上下排列，但两图都保留。

### 3.2 本方案不包含

- 下单、撤单、账户、持仓盈亏、保证金和交易网关接入。
- 商品期权、股指期权、股票期权。
- 外盘期货、外汇、数字货币。
- Tick 级盘口深度、逐笔成交回放、量化策略和自动交易。
- 复权式连续合约算法。第一版展示数据源提供的主力连续序列，并显式披露换月跳空；自建前复权/后复权连续序列另立需求。

## 4. 核心产品规则

### 4.1 合约输入与展示

用户输入应支持大小写和常见别名：

| 用户输入 | 解析结果 | 说明 |
|---|---|---|
| `rb2510` / `RB2510` | 具体合约 `RB2510` | 自动识别品种和交易所 |
| `RB0` / `rb主连` / `螺纹主连` | 连续序列 `RB0` | 页面标注“主连/不可交易” |
| `nf_rb2510` / 旧格式 `nfrb2510` | 迁移为 `RB2510` | 仅兼容旧存储和旧输入，不作为内部标识 |
| `IF2603` | 中金所具体合约 | 采用金融期货会话规则 |

同一品种代码在不同交易所发生歧义时，不静默猜测；必须要求用户从候选项中选择。过期、未上市或数据源不支持的合约保留输入值并显示可理解的错误，不自动替换成主力合约。

### 4.2 内部标识

`nf_` 是新浪供应商协议的一部分，不应继续充当领域模型。内部统一使用：

```js
{
  id: 'future:shfe:RB2510',
  type: 'future',
  exchange: 'shfe',
  product: 'RB',
  symbol: 'RB2510',
  contractKind: 'specific', // specific | continuous | main
  providerSymbols: {
    sina: 'nf_RB2510',
    akshare: 'RB2510'
  }
}
```

- `id` 是监控列表、localStorage、请求去重和共享缓存的主键。
- `symbol` 是界面主代码；`providerSymbols` 只能存在于数据源适配层。
- 连续序列使用独立 ID，例如 `future:shfe:RB0`，不得与当前主力具体合约共用缓存。
- 动态“主力合约”若解析到 `RB2510`，界面必须同时显示“螺纹主力 → RB2510”和解析时间。

### 4.3 涨跌口径

期货默认采用“最新价相对昨结算价”计算涨跌，而不是股票的昨收口径：

```text
change = lastPrice - previousSettlement
changePercent = change / previousSettlement * 100%
```

- 卡片和语音文案使用“较昨结”。
- `previousClose`、`previousSettlement`、`settlement` 分字段保存，不得互相代替。
- 数据源缺少昨结时，涨跌显示 `--` 并标注字段缺失，不能以 0 参与计算。
- 具体合约和连续序列使用各自数据源给出的基准，不跨合约拼接昨结。

### 4.4 双图布局与交互

选中期货行后必须同时出现：

- 左侧分时图：当前交易日完整分时，包含前一自然日晚间开始的夜盘；价格线、昨结线、均价线、成交量，数据允许时增加持仓量副图。
- 右侧 K 线：1/5/15/30/60 分钟及日/周/月切换；蜡烛、成交量和持仓量；显示当前所选周期和数据更新时间。

共同要求：

- 两张图均有 loading、空数据、错误、陈旧缓存四种明确状态。
- 十字光标限定在各自容器内，tooltip 不得溢出到页面左上角或遮挡另一张图。
- 实时刷新通过 `series.update()` 更新最后一点/最后一根柱；任何单次增量错误都不能退化为 `setData([bar])` 清空历史。
- 夜盘跨午夜时横轴连续，但 tooltip 同时展示“交易日”和自然日期时间。
- 休盘区间不伪造价格点；可用视觉间隔表达 10:15—10:30、午间和夜盘后的停盘。
- 连续合约图明确显示换月标记；第一版不平滑换月跳空。

### 4.5 刷新与状态

- 交易中：默认 3 秒刷新报价；分时/K 线按请求预算 10—30 秒增量刷新。
- 集合竞价、连续交易、节间休市、闭市分别建模，不复用 A 股的单一 `trading` 布尔值。
- 交易中断线时展示最后成功时间和重试状态，不清空行情和图表。
- 恢复网络后立即刷新，不受旧的一小时最小强刷年龄限制。
- 页面不可见时可降低频率，但价格提醒开启时仍需遵守浏览器能力边界并在 UI 中说明。

## 5. 期货交易日与会话模型

期货“交易日”不等于自然日。商品期货夜盘通常从前一工作日 21:00 开始，跨午夜的行情仍属于次一交易日；不同品种夜盘结束时间可能为 23:00、01:00 或 02:30。中金所品种又有独立日盘规则。因此不得使用固定的股票时段函数判断全部期货。

建议数据模型：

```js
{
  exchange: 'shfe',
  product: 'AU',
  tradingDay: '2026-09-04',
  sessions: [
    { start: '2026-09-03T21:00:00+08:00', end: '2026-09-04T02:30:00+08:00', kind: 'night' },
    { start: '2026-09-04T09:00:00+08:00', end: '2026-09-04T10:15:00+08:00', kind: 'day' },
    { start: '2026-09-04T10:30:00+08:00', end: '2026-09-04T11:30:00+08:00', kind: 'day' },
    { start: '2026-09-04T13:30:00+08:00', end: '2026-09-04T15:00:00+08:00', kind: 'day' }
  ]
}
```

实现规则：

1. 会话配置按“交易所 + 品种 + 生效日期”版本化，不能只按交易所硬编码。
2. 节假日和临时调整优先使用交易所/日历数据；法定节假日前最后工作日晚间通常无夜盘，不能仅凭工作日推算。
3. 每条行情同时保存 `timestamp`、`naturalDate`、`tradingDay`。
4. 交易状态至少包含 `pre-open`、`auction`、`trading`、`session-break`、`after-close`、`closed`、`unknown`。
5. 会话规则过期或无法确定时返回 `unknown` 并维持低频刷新，不能错误地停止全部刷新。

交易所规则可能调整，文档只定义模型，不把当前时刻表当永久常量。上期所公开材料明确列出了按品种区分的 23:00、01:00、02:30 夜盘结束时间，并将前一工作日夜盘至当日日盘视为同一交易日；中金所股指期货的日盘则为 09:30—11:30、13:00—15:00。实际发布时应再次核验最新交易所通知。

## 6. 数据源方案

### 6.1 原则

- 浏览器只请求本项目 `/api/cache/futures/*`，不直接耦合新浪或 AKTools。
- 服务端负责供应商协议、GBK 解码、超时、限流、缓存、回退和字段归一化。
- 每种数据必须有明确主源、备源和“最后成功缓存”策略；主备返回空都不能被当作成功覆盖有效缓存。
- 启动时做 AKTools 能力探测，确认本机版本实际暴露所需接口；“AKShare 文档支持”不等于“当前 AKTools 实例已经可用”。

### 6.2 建议数据源矩阵

| 能力 | 主源 | 备源 | 备注 |
|---|---|---|---|
| 合约/品种目录 | AKTools 调用 AKShare 合约信息及 `futures_display_main_sina` | 项目内版本化静态目录 | 静态目录只能兜底，不替代过期校验 |
| 主力具体合约解析 | AKTools `match_main_contract` | 最近成功映射 | 保存解析时间和来源 |
| 实时报价 | AKTools `futures_zh_spot` | 服务端直连新浪 `nf_` 行情 | 商品 `CF`、金融 `FF` 分开请求 |
| 1—60 分钟数据 | AKTools `futures_zh_minute_sina` | 最后成功缓存 | 返回 OHLCV 和持仓量 |
| 具体合约日线 | AKTools `futures_zh_daily_sina` | `get_futures_daily` 交易所数据 | 周/月线优先由已验证日线聚合 |
| 连续合约日线 | AKTools `futures_main_sina` / `futures_zh_daily_sina(*0)` | 最后成功缓存 | 明示连续序列来源和换月跳空 |
| 交易日历/临时调整 | 交易所/AKShare 日历 + 项目配置 | 工作日推断，仅降级 | 推断状态必须标记 `degraded` |

AKShare 当前公开文档列出的接口已覆盖本方案核心字段：`futures_zh_spot` 提供实时价、买卖价、成交量、持仓量、昨收和昨结；`futures_zh_minute_sina` 提供 1—60 分钟 OHLCV 与持仓量；`futures_zh_daily_sina` 同时支持具体合约和 `RB0` 一类连续合约；`futures_main_sina` 提供主力连续日频历史。它们可作为 AKTools 适配层候选，但上线前仍须逐接口实测返回契约、频率限制和空响应语义。

## 7. 标准数据契约

### 7.1 实时报价

```js
{
  instrumentId: 'future:shfe:RB2510',
  type: 'future',
  exchange: 'shfe',
  product: 'RB',
  symbol: 'RB2510',
  name: '螺纹钢2510',
  contractKind: 'specific',
  tradingDay: '2026-09-04',
  timestamp: 1788451260000,
  lastPrice: 3280,
  previousSettlement: 3268,
  previousClose: 3272,
  settlement: null,
  open: 3270,
  high: 3291,
  low: 3258,
  bidPrice1: 3279,
  askPrice1: 3280,
  bidVolume1: 12,
  askVolume1: 8,
  volume: 123456,
  openInterest: 987654,
  change: 12,
  changePercent: 0.37,
  source: 'aktools-futures_zh_spot',
  fetchedAt: 1788451261200,
  stale: false
}
```

所有缺失数字使用 `null`，不能把缺失字段转成 0。解析器必须验证字段数量、时间戳、正价格、交易日以及合约是否与请求相符。

### 7.2 K 线/分时

```js
{
  instrumentId: 'future:shfe:RB2510',
  period: '1m',
  tradingDay: '2026-09-04',
  items: [{
    time: 1788451260,
    open: 3279,
    high: 3281,
    low: 3278,
    close: 3280,
    volume: 3485,
    openInterest: 1739947,
    tradingDay: '2026-09-04'
  }],
  source: 'aktools-futures_zh_minute_sina',
  fetchedAt: 1788451261200,
  stale: false,
  complete: false
}
```

- 时间统一为北京时间解析后的 Unix 秒，禁止依赖浏览器本地时区隐式转换。
- 分钟量若数据源给出累计量，适配层转换为单柱量并记录算法；若不能确认语义，不显示伪造的柱量。
- `complete` 依据该合约对应交易日的最后会话是否结束，而不是固定 15:00。

## 8. 后端与前端架构

### 8.1 新增服务端模块

建议新增：

```text
server/futures/
├── contractCatalog.js       # 合约目录、别名、交易所与品种映射
├── futuresProviders.js      # AKTools/Sina 供应商适配器
├── futuresQuoteService.js   # 实时报价主备、校验、single-flight
├── futuresKlineService.js   # 分钟/日线获取与周月聚合
├── futuresSessionService.js # 交易日和分段会话
└── futuresSchemas.js        # 标准契约校验与序列化
```

新增 API：

| 路径 | 用途 |
|---|---|
| `GET /api/cache/futures/contracts?q=` | 搜索/解析合约与别名 |
| `GET /api/cache/futures/quote?ids=` | 批量标准化实时报价 |
| `GET /api/cache/futures/intraday?id=&tradingDay=` | 一个交易日的完整分时 |
| `GET /api/cache/futures/kline?id=&period=&from=&to=` | 分钟/日/周/月 K 线 |
| `GET /api/cache/futures/session?id=&at=` | 会话状态与交易日归属 |

所有参数必须先完成白名单解析和长度限制，再进入上游请求和缓存路径；缓存文件名不得直接拼接未清洗用户输入。

### 8.2 前端拆分

期货功能不能继续堆进已超过 3,800 行的 `app.js`。建议新增：

```text
src/js/futures/
├── instrument.js       # 输入解析、ID 与供应商代码转换
├── futuresApi.js       # 仅调用本项目标准 API
├── futuresSession.js   # 前端状态展示，不自行猜交易日
├── futuresPresenter.js # 字段、涨跌口径和文案
└── futuresCharts.js    # 双图控制器和增量更新
```

股票与期货共用监控列表外壳、提醒和 TTS 调度，但数据获取、会话、字段展示和图表控制器按资产类型分离。共享层只能依赖标准 Quote/Bar 契约，不出现 `nf_`、新浪字段下标或 AKShare 中文列名。

### 8.3 缓存与并发

缓存键必须包含：

```text
futures/quote/{instrumentId}.json
futures/intraday/{instrumentId}/{tradingDay}.json
futures/kline/{instrumentId}/{period}.json
futures/contracts/catalog.json
futures/contracts/main-map.json
```

- 实时报价 TTL：交易中 2—3 秒，休盘 30 秒，闭市 5 分钟。
- 当前交易日分钟数据 TTL：交易中 10—30 秒，闭市且确认完整后长期保存。
- 历史日线 TTL：已完成历史区间长期保存；当日柱在最终结算数据出现前保持可刷新。
- 空响应只短暂缓存 15—60 秒，并保存错误原因；不得覆盖非空成功缓存。
- 同一 key 使用 single-flight，但调用方 AbortSignal 只能取消自己的等待，不能取消其他消费者共享的上游请求。
- 磁盘写入使用随机 UUID 临时名、原子替换和失败清理；读取命中不得为了 touch 每次重写整个数据文件。

## 9. 降级、可观测性与安全

### 9.1 用户可见状态

每个行情和图表区域必须显示：

- 数据源及最后更新时间。
- `实时`、`延迟`、`缓存`、`降级`、`已闭市`、`未知会话`之一。
- 主源失败后的备源切换，不把“缓存成功”冒充“实时成功”。
- 连续合约不可交易和换月跳空提示。

### 9.2 服务端诊断

诊断信息至少包含 provider、endpoint、instrumentId、period、duration、resultCount、cacheStatus、stale、errorClass；日志不得记录用户无关隐私或完整响应体。

健康检查应分别报告：

- AKTools 连接状态和所需期货接口能力。
- 新浪直连状态。
- 合约目录更新时间。
- 会话规则版本和最后校验时间。
- 各数据源连续失败数、冷却状态及最近成功时间。

### 9.3 数据展示免责

页面注明行情来自公开数据源，可能延迟或中断，仅供监控参考，不构成交易建议。没有可靠数据时宁可显示陈旧标记或错误，也不能编造 0 值、沿用错误合约或静默切换主力。

## 10. 实施顺序

期货建设应在两份代码审查 handoff 中与数据正确性、崩溃和图表有关的高优先级缺陷稳定后开始，避免在不可靠基础上继续扩张。

## 12. 风险与待确认决策

### 12.1 已确定

- 保留左分时、右 K 线双图同时显示。
- 不在本轮实现期权、外盘和下单。
- `nf_` 只作为供应商代码，不作为内部领域 ID。
- 涨跌默认以昨结算价为基准。
- 连续合约明确标识不可交易，第一版不做跳空复权。
- 先修复现有高优先级正确性/稳定性缺陷，再展开期货功能。

### 12.2 实施前仍需产品确认

1. “主力”默认展示数据源连续序列，还是展示动态解析到的可交易具体合约；建议两者都支持并明确区分。
2. 持仓量采用独立副图还是与成交量共享副图切换；建议桌面端双副图，移动端切换。
3. 是否需要内置默认期货自选列表；建议首版不预置，避免过期合约。
4. 提醒是否增加绝对价格、持仓量变化和突破高低点；建议首版先复用涨跌幅/价格阈值，后续单列增强需求。

## 14. 完成定义

“期货功能完成”必须同时满足以下条件：

1. 具体合约和连续/主力合约能被正确识别、持久化并明确区分。
2. 真实实时报价在对应日盘/夜盘持续刷新，涨跌按昨结正确计算。
3. 左分时与右 K 线同时可用，且都随价格变化增量更新。
4. 夜盘跨自然日仍归属正确交易日，休盘和节假日不会错误停刷或错误续刷。
5. 成交量、持仓量、昨结、结算等期货字段不以 0 冒充缺失值。
6. 主源失败可降级，空响应不破坏成功缓存，状态对用户透明。
7. 语音、提醒、持久化、移动端和长时间运行均通过验收。
8. 自动化 CI、真实数据源 smoke test、实际交易时段双图更新证据全部具备。

缺少其中任何一项时，应准确标记为“部分期货支持”，不能仅凭实时报价接口可调用就宣布完整完成。
