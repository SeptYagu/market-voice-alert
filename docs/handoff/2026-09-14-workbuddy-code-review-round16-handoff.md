## 二、审查发现与缺陷清单

### P3（低）§2.2/§3 的 320 根滑动窗口保留根数与滑出阈值以「每个交易日恰为 240 根」为隐含前提，却以「严格服从」作全称断言；同一 241/243 根/日前提在 T-1 分支已被补条件，T-2 分支与 4 处同类表述未同步

- **文件与行号**：
  - 主实例：`docs/handoff/2026-09-14-limit-up-chart-date-flip-investigation-and-resolution-handoff.md:68` —— 「T-2 在 320 根窗口中的实际保留根数**严格服从**公式 $\max(0, 80 - x)$……T-2 仍有 $\max(0, 80 - x)$ 根 Bar 留在窗口内（**1~80 根**，例如 09:30 开盘 $x=0$ 时剩余 80 根）；**只有当盘中生成 Bar 数 $x \ge 80$ 后**，T-2 才被物理完全滑出 320 根窗口」。
  - 同源前提：同文件 `:67`「**前一天（T-1）**：窗口剩余容量为 $\min(240, 320 - x)$ 根……盘前未开盘 $x=0$ 时则容纳完整 **240** 根」——式中 `240` 同时充当「T-1 当日 Bar 数」与「单日上限」。
  - 同一命题的其余 3 处未同步（同类表述横向扫描缺口）：`:29`（§2 mermaid 节点 K：「当日 Bar ≥ 80 (约 10:48 后) 320 根窗口完全滑出 T-2 (命中 0 根)」）、`:138-139`（§3 第 2 点：「滑动窗口物理耗尽（盘中**第 80 根 Bar** 之后）」「处于 **10:48 之后**时，T-2 跌出了 320 根滑动窗口的物理极限」）、`:143`（§3 结论：「用户在 **10:48 之后**查看 T-2 时，T-2 已滑出 320 根窗口」）。
  - 被自述前提反证：同文件 `:65`「A 股每个常规交易日标准包含 240 根 1 分钟 Bar（……**若腾讯等数据源计入 9:25 开盘集合竞价点则为 241/243 根**）」；`STATUS.md:96`（round 13 闭环段）亦写「若计入早盘 09:25 集合竞价等导致**单日**产生 241 或 243 根 Bar，则收盘保留约 77~79 根」。而 `:63` 已明确该 320 根窗口取自 `tencent-legacy` 1m 缓存——即 T-1、T-2 与当日同源。round 13 只为 T-1 的「恒 ≥80」补了「**当日 x ≤ 240**」条件（today 维度），**「历史日自身为 241/243 根」这一维度从未处理**。
- **触发条件**：东财 1m 冷却回退腾讯 320 源、且 AKTools 历史分钟源不可用（文档 §2.2.3 既定前提），且 T-1 本身是计入 9:25 集合竞价点的 241/243 根交易日。此时 T-2 在窗口中的保留根数为 `max(0, 320 - x - n)`（`n` = T-1 当日 Bar 数），而非 `max(0, 80 - x)`。
- **实际行为与期望行为**：
  - 期望（文档 `:68` 自述）：T-2 保留根数「严格服从」`max(0, 80-x)`，区间恒为 `1~80`，滑出阈值为 `x ≥ 80`（约 10:48）。
  - 实际：`x=0` 时 T-2 保留 `80 / 79 / 77` 根（`n = 240 / 241 / 243`）；滑出阈值相应为 `x ≥ 80 / 79 / 77`（约 10:48 / 10:47 / 10:45）；`x=0` 时 T-1 实际在窗口内为 `240 / 241 / 243` 根，`:67`/`:71` 的「240 根」仅对 `n = 240` 成立。
- **根因**：文档的滑动窗口模型把 `320 − 240 = 80` 当作常量，`240` 同时承担「单日 Bar 数」与「T-1 上限」双重角色；同一小节 `:65` 已声明该单日长度可被集合竞价点抬到 241/243，但**该前提只在 T-1 分支被部分吸收（`:71` 仅覆盖「当日 x 达 241/243」的情形）**，T-2 分支与 §3 的 4 处复述仍以未标注的「240 根/日」为前提。属本仓库审查史中已反复出现的「同一命题未做横向一致性扫描」同族变体（round 12 P3-1、round 13 P3-3 的残留维度）。
- **影响范围**：仅影响根因章节的量化严谨性（本轮无产品代码/测试改动，无运行期影响）。`x ≥ 80` 是本方案「为什么只有前一天被伪装锁死、前两天暴露真实缺省」这一核心叙事的时间判据（mermaid 节点 K、§2.2.3 第 2 条、§3 第 2/3 点）；按当前未加前提的写法落地用例或复核时，T-2 滑出阈值会被错置在最坏情形下 3 根 Bar（约 3 分钟）。主线结论（T-1 恒在覆盖带内、T-2 最终物理滑出）不受影响。
- **复现方法/验证证据**（仓库外探针 `%TEMP%/r16probe/window.mjs`，未入库；纯算术回放，公式取文档 `:67`/`:68` 原文）：
  ```

  ```
- **修复建议**（仅文档，不涉及产品代码与测试）：
  1. 将 `:68` 的公式改为通用形式 `max(0, 320 - x - n)`（`n` = T-1 当日 Bar 数），或保留 `max(0, 80 - x)` 但显式标注「**前提：T-1 为常规 240 根**」，并同句补出 `n = 241 / 243` 时的 `max(0, 79 - x) / max(0, 77 - x)` 与上限 `79 / 77` 根；
  2. 同批同步 `:29`（mermaid 节点 K）、`:138-139`、`:143` 的滑出阈值表述 —— 由「第 80 根 Bar / 约 10:48」改为「第 77~80 根 Bar / 约 10:45~10:48（视 T-1 是否计入集合竞价点）」，或统一加注前提；
  3. 同批为 `:67` / `:71` 的 `min(240, 320 - x)` 与「x=0 时为完整 240 根」补上「T-1 为常规 240 根」前提（`n = 241/243` 时上界相应放宽至 241/243）；
  4. **不得**回填改写 `STATUS.md` 各历史段（含 round 13 段 `:96` 的「单日 241/243 根」引文与 round 12 段的「恒 ≥80」引文），修复只作用于当前方案文档（避免重演 round 14 P3-1 的「历史引文回填」缺陷）。
- **修复后验收标准**：全文（含 mermaid、§2.2、§3 复述）任一 T-1/T-2 保留根数与滑出阈值表述，均可由通用式 `max(0, 320 - x - n)`（`n ∈ {240, 241, 243}`）复算得出，或已显式标注成立前提；不存在未带前提的「严格服从」式定值/固定区间；`STATUS.md` 全部历史段引文仍可逐字复核、未被回填。
