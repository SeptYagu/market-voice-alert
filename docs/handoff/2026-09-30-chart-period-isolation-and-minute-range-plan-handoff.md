- 日期：2026-09-30。
- 状态：已完成源码检查和本地确定性复现；本文件是修复方案，功能代码尚未修改。
- 检查基线：`166ccc9a99bcdc690ae39215ed023488c215eeac`，`main`；开始检查时工作区干净，`git pull --ff-only` 显示已同步。
- 用户目标：切换 K 线周期只更新 K 线，分时图保持原状；分钟 K 线末根柱只显示该周期的价格范围。
- 验证方式：调用真实生产模块，使用固定时间、行情夹具和请求替身。未使用真实行情，也未在浏览器中进行本次视觉验收。

## 1. 检查结论

| 问题 | 结论 | 直接原因 |
| --- | --- | --- |
| 切换 K 线周期后分时图一起刷新 | 已复现，存在状态、请求和 DOM 三层耦合 | 周期切换清空分时状态；K 线加载完成必定触发分时加载；监控页状态回调重绘整个表格并销毁两张图 |

## 2. 问题一：周期切换影响分时图

### 2.1 现有调用链与证据

1. 监控页 `src/js/app.js:1310` 的 `handlePeriodChange` 调用 `ChartRowManager.handlePeriodChange`。
2. `src/js/controllers/chartRowController.js:521-547` 更新 K 线周期时，同时清空 `selectedTradeDate`、`manualTradeDate`、`intradayData`、`intradayError` 和分时视窗状态，并取消分时请求。
3. `loadKline` 在 `chartRowController.js:413-415` 无条件对双图管理器调用 `loadIntraday`。因此，即便保留分时数据，仍会发生额外请求和 `setData`。
4. 管理器在 `app.js:404` 的状态回调调用 `renderData`；`app.js:765` 再调用 `renderTable`。`renderTable` 的 `beforeRerenderClean`（约 636-652 行）销毁全部展开标的的 K 线及分时实例；`src/js/views/monitorTableView.js:274-278` 清空表格 DOM 后重建。问题可能波及其他已展开标的。
5. 涨停页 `src/js/controllers/limitUpController.js:590-607` 的 `handleLimitUpKlinePeriodChange` 自行清空分时数据并调用 K 线加载。该入口没有复用管理器的周期切换方法；涨停视图已有增量更新路径（`src/js/limitUpView.js:729-738`），应保留和利用它。

### 2.2 本地复现

以真实 `ChartRowManager` 和 `createChartState` 建立状态：周期为日 K，分时日期为 `2026-09-29`，`manualTradeDate=true`，分时数据已存在，分时请求带取消计数。将 `loadKline` 替换为计数器，调用 `handlePeriodChange('5m', 'sh600519')`。

实际结果：

```text
selectedTradeDate = null
manualTradeDate = false
intradayData = null
intradayAbort.abort 调用次数 = 1
loadKline 调用次数 = 1
```

另建 5 分钟图状态，使用请求替身返回一根合法 K 线，调用真实 `loadKline`，将 `loadIntraday` 替换为计数器：K 线成功加载后，分时加载计数为 **1**，K 线错误为 `null`。

DOM 销毁路径由源码确认，本次未计量真实浏览器闪烁次数。

### 2.3 修复方案

将 K 线周期和分时交易日作为两个独立维度：周期切换只更新目标标的的 K 线状态。

1. **保留分时状态和请求身份**：周期切换不清空分时日期、手动日期选择、数据、错误、加载/刷新标记、最近抓取时间和视窗状态，不取消分时请求或重建其请求作用域。仅取消旧 K 线请求并重置 K 线数据、错误和视窗。
2. **明确加载目的**：为 `loadKline` 增加显式的分时联动选项（例如 `reloadIntraday`）。周期切换与仅 K 线的后台重载传 `false`；首次展开仍初始化分时。保留现有“重新加载”按钮语义，实施时用单独用例确认其是否联动双图。不得简单删除全部分时加载调用。
3. **局部更新图表区域**：监控页的周期切换及该次加载结束回调只更新目标标的周期按钮、K 线状态、K 线数据和必要尺寸，不进入整表 `renderData` 重建路径；也不重建其他标的图表。可复用现有 K 线控制器的 `setPeriod` 和数据更新方法。不能仅保留分时数组而继续销毁其 DOM/控制器。
4. **统一涨停页入口**：让涨停页周期切换复用修正后的管理器逻辑，或明确实现相同契约；保留涨停视图既有增量 DOM 更新。
5. **保留独立刷新职责**：点击另一交易日、正常定时分时刷新、实时 tick、关闭/重开图表仍按各自规则运行。所谓“不跟着刷新”是指周期切换不额外触发分时请求、重绘或取消，不能因此停止正常实时更新。
6. **处理并发**：快速切换周期仍通过 K 线请求作用域、实例和周期身份拦截旧响应；切换期间点击分时日期由分时自身作用域决定有效响应，K 线响应不得覆盖它。

### 2.4 现有测试需要调整

`tests/chartRowController.test.js:232` 的用例明确要求周期切换取消分时请求、清空日期和数据，固化了当前错误行为。实施时将其改为“分时身份、数据和请求保持，旧 K 线请求取消”，并补 UI 层实例及 DOM 保持断言。不能只删除原用例。

## 3. 问题二：分钟 K 线末柱被全天高低价污染

### 3.1 现有调用链与证据

- 首次获取 K 线后：`ChartRowManager.loadKline`（`chartRowController.js:395-405`）把当前完整报价交给 `applyLiveQuoteToKline`。
- 实时更新：`applyLiveTickToKlineChart`（`chartRowController.js:117-127`）收到报价对象同样调用该函数；`app.js:1356` 起的双页实时循环走这一入口。
- `src/js/kline.js:734-738` 的通用合并计算 `max(last.high, quote.high, price)` / `min(last.low, quote.low, price)`，分钟周期也落入这里。
- `applyLiveTickToKline`（`kline.js:433`）仅收到价格时，分钟高低价只和最新价合并；但生产完整报价路径没有使用这一隔离口径。

因此，既有数据即便来自正确的分钟接口，也可在显示前被全天高低价污染；后续每次完整报价更新继续污染。删除实时更新中的日高低价还不够，加载后的报价合并也必须修复。

### 3.2 本地确定性复现

固定北京时间为 `2026-09-30 10:03`，调用真实 `applyLiveQuoteToKline`：

| 字段 | 接口分钟柱 | 当前报价 |
| --- | --- | --- |
| 时间 | `2026-09-30 10:00` | `updateTime=20260930100300` |
| 开盘 | 100 | 全天开盘 95 |
| 最高 | 102 | 全天最高 120 |
| 最低 | 99 | 全天最低 80 |
| 收盘/最新价 | 101 | 101.5 |
| 成交量 | 200 | 全天累计 100000 |

分别传入 `1m/5m/15m/30m/60m`，五个输出均为：

```text
open=100, high=120, low=80, close=101.5, volume=200
```

输入数组未被原地修改，但输出柱被污染。以确认属于同一在途周期的报价为前提，正确价格范围应是 `high=102, low=99`，收盘为 `101.5`，不能吸收全天 120/80。

注意：上述 1 分钟夹具的末柱时间与报价相差 3 分钟，同时暴露“无周期归属检查便更新末柱”的相邻风险；它证明全天高低价泄漏，不能用来证明同周期更新正确。正式测试应另用匹配各周期边界的时间夹具。

### 3.3 修复方案

1. **隔离分钟周期合并**：在通用日/周/月极值合并之前处理 `isMinutePeriod(period)`。分钟柱的 OHLCV 来源只能是该周期权威 K 线与确认属于该周期的实时成交价格；不能使用日累计 `quote.open/high/low/volume/amount/changePercent` 覆写分钟指标。
2. **同周期 tick 更新**：确认报价时间落在末柱所在周期后，保持该柱 `open`，更新 `close=price`、`high=max(last.high, price)`、`low=min(last.low, price)`。已有周期成交量和成交额保留；轮询快照不能保证捕获周期内所有成交，应由周期接口校准。
3. **先明确时间契约**：核对东财/腾讯及各资产族分钟数据的时间字段是周期起点还是终点，按实际交易会话和端点规则匹配。不能仅按北京时间整点取模；午休、夜盘、跨日和外盘会话须分别验证。
4. **过期或归属未知时不改历史柱**：旧日期、旧周期、无可验证时间戳的报价不得当作末柱实时成交写入。价格数字形式的兼容入口也须明确保守策略，避免绕过时间门控。
5. **跨周期采用权威重载**：报价已进入下一周期或无法验证归属时，保持已完成柱，触发限频、可取消、身份受保护的当前周期 K 线重载，且不联动分时。不从日累计字段构造新分钟 OHLCV，不从稀疏轮询伪造缺失周期。现有 `refreshPreviewKline` 仅处理日 K 预览柱，不能直接认为已覆盖分钟重载。
6. **已有污染必须恢复**：实施后重新请求权威分钟 K 线替换受污染末柱；不能期待后续 `max/min` 自动缩回。核查污染是否写回持久化缓存，若确认存在，只清理/重验证相关缓存键，避免无依据全量清缓存。
7. **保持其他周期规则**：日 K 仍可使用当日官方报价字段；周/月允许吸收当日极值，但不使用日累计量替换聚合量；原集合竞价 Fail-Closed 门控不得放宽。

建议先完成双图刷新解耦，再修分钟数据边界和重载；各阶段分别验证、提交、推送，并按仓库流程进行独立审查。本次只交付检查文档。

| 验收项 | 必须满足的结果 |
| --- | --- |
| 监控页日 K → 5 分钟 → 15 分钟 | 仅目标 K 线更新；分时实例、DOM、日期、数据保持；周期操作产生的分时请求增量为 0 |
| 涨停页同样切换 | 同一契约，覆盖其独立入口 |
| 多个标的同时展开 | 切换 A 不销毁 A 的分时图，不重建 B 的任何图 |

| 分时请求尚未结束 | 周期切换不取消请求；有效分时响应仍可提交 |
| 连续快速切换 / 期间选日期 | 旧 K 线响应不能覆盖新周期，K 线响应不能重置新分时日期 |
| K 线加载失败 | 分时图保持可见并继续独立工作 |
| 首次展开 / 点击另一交易日 / 正常定时刷新 | 分时初始化及独立刷新行为正常 |

| 同周期价突破该柱高点 / 低点 | 只按该周期真实新价扩大极值 |
| 下一周期、跨日、午休、夜盘、时间戳缺失/过期 | 不污染已完成柱；权威重载限频，旧响应不能提交 |
| 加载时报价合并 + 后续实时报价 | 两条路径均满足分钟隔离规则 |
| 日/周/月与集合竞价 | 原有合法极值、聚合量与时效门控规则保持 |

验证要求：控制器和纯函数回归用例需在修复前实际失败，修复后通过；浏览器测试要同时检查请求增量、控制器/DOM 身份与可见数据，不能只检查画布存在。隔离正常定时刷新后统计“由周期操作产生”的请求，避免把正常行情更新误判为缺陷。

正式代码交付运行 `npm run lint`、`npm test`、`npm run e2e`、`npm run build`，并检查双页视觉效果。本次检查未运行完整代码门禁，因为未修改功能代码；本地复现结果不代表已修复。
