# 2026-09-02 运行时 Bug 与行情图表对照 Handoff

## 范围与结论

本轮暂不处理期货，只检查现有股票功能。已在本机真实启动 Vite 与 AKTools，并用浏览器访问真实数据源。

确认两个主要问题：

1. `10日涨幅超45%` 当前无法完成全市场扫描。根因是全市场股票池只有 AKTools `stock_zh_a_spot_em` 一个入口；该接口调用东财时发生 `RemoteDisconnected`，服务端写入 `status: "error"`、`universeSize: 0`。前端把这个错误缓存当作有效响应并直接返回，按钮不会触发重扫，也不会进入旧的浏览器端回退扫描。
2. 当前图表虽然能绘制 K 线，但信息架构和国内主流行情页差距明显：在用户明确要求的左右双图布局内，两个半宽画布仍缺少针对窄画布的刻度与信息密度设计；同时缺少紧贴图表的 OHLC/涨跌/成交量图例、清晰的均线图例、指标副图和完整行情上下文。本次还连续复现到分时图 `HTTP 500`，而日 K 正常。

下文前半部分保留首次复现证据；本轮随后已进入修复与验证，最新实施状态见文末“2026-09-02 修复实施记录”。

## 10 日涨幅扫描：复现证据

页面点击“扫描”后显示：

```text
错误: fetch failed
暂无结果
```

服务端接口：

```text
GET /api/cache/momentum/ten-day?date=20260902&threshold=45
HTTP 200
source: stale
stale: true
data.status: error
data.universeSize: 0
data.scanned: 0
data.error: fetch failed
```

缓存文件：

```text
data/cache/momentum/20260902/ten-day-45pct.json
```

AKTools 直接请求：

```text
GET http://127.0.0.1:8888/api/public/stock_zh_a_spot_em
HTTP 500
```

直接执行 `akshare.stock_zh_a_spot_em()` 的底层异常为：

```text
requests.exceptions.ConnectionError:
('Connection aborted.', RemoteDisconnected('Remote end closed connection without response'))
```

### 根因链

1. `server/marketData.js` 的 `fetchAktoolsSpot()` 只调用 `stock_zh_a_spot_em`。
2. `server/spotService.js` 没有第二全市场来源；上游断开后无法得到 universe。
3. `server/momentumService.js` 的 `buildMomentum()` 必须先取得 spot universe，因此在 K 线扫描前就失败。
4. 错误被保存成缓存数据，`GET /api/cache/momentum/ten-day` 仍返回 HTTP 200。
5. `src/js/app.js` 的 `handleMomentumScan()` 收到 `cached.status === 'error'` 后设置错误并 `return`，不会执行后面的前端 fallback。
6. 当前 API 被设计为只读缓存状态，实际启动扫描只发生在服务启动、北京时间 08:00 和 15:01。页面仍显示“扫描”按钮，但用户无法主动恢复失败任务。

### 测试缺口

`e2e/helpers.js` 始终 mock `status: "complete"` 的 momentum 响应。当前没有覆盖：

- spot 上游 500/断连；
- momentum `status: "error"`；
- 用户点击按钮后的真实重试；
- 上一次成功结果与本次失败任务状态的隔离。

因此现有 CI 全绿不能证明该真实链路可用。

### 成功加载实测

在交易时段重新打开贵州茅台图表，分时最终成功，但从展开股票到分时完成约等待 21 秒：

```

对应缓存：

first: 09:30
last: 13:02
lastClose: 1298.00

```

这不是主分时源成功，而是最后一级的 1 分钟 K 线降级结果。两个 AKTools 分时接口现场测试均失败：

| 接口 | 结果 | 耗时 |
|---|---:|---:|
| `stock_intraday_em` | HTTP 500 | 3.071 秒 |
| `stock_zh_a_hist_min_em` | HTTP 500 | 3.551 秒 |

### 分时失败链为什么又慢又不稳定

1. 服务端依次请求 AKTools 成交明细、AKTools 历史分钟、服务端 K 线备用，完全串行。
2. 服务端失败后，前端静默吞掉共享缓存错误，又依次重复 AKTools 成交明细、AKTools历史分钟、东财 trends2、浏览器 K 线备用。
3. 即同一页面可能重复访问相同故障上游，形成双层串行 waterfall。
4. 页面只有笼统的“分时加载中”或最后一个错误 `HTTP 500`，看不到当前尝试的数据源、已耗时、重试阶段和是否还能降级。
5. 服务端路径没有前端已有的东财 `trends2` 备用，服务端和浏览器 fallback 链不一致。
6. 最终错误只抛出 `errors` 数组最后一项，前面各数据源的错误全部丢失，无法诊断是主源失败、备用为空还是最后 K 线失败。

### 交易时段实时更新实验

在同一个已展开图表页面等待一个 10 秒刷新周期以上，得到：

```text
T0
表格现价: 1299.02
分时状态: 123 点 · 1298.00 · -0.12%

T+12.5 秒
表格现价: 1298.99
分时状态: 123 点 · 1298.00 · -0.12%
```

截图中右侧日 K 的最后价格标签同步变成 `1298.99`，左侧分时仍停在 `1298.00`。

结论：

- **监控表格：会更新。**
- **右侧 K 线：只更新最后一根的 close 和由 close 计算的 MA。**
- **左侧分时：加载完成后完全不随定时行情刷新更新。**
- **K 线的当日 high、low、volume、amount：不更新。**

源码证据：

- `refreshNow()` 只调用 `updateChartLastTickMulti()`。
- `updateChartLastTickMulti()` 只调用 K 线的 `applyLiveTickToChartForCode()`，没有任何 intraday update。
- `createIntradayChart()` 返回值只有 `setData()`，没有 `update()` 或追加分钟点能力。
- `applyLiveTickToKline()` 对日/周/月明确只改 `close`，测试还断言 `high`、`low`、`volume` 必须保持不变。
- `updateVolume()` 虽然每次被调用，但传入的是未更新的旧 volume，所以视觉上的当日成交量仍冻结。

现场日 K 缓存最后一根为：

```text
date: 2026-09-02
open: 1302.80
high: 1303.00
low: 1291.20
close: 1295.12
volume: 11700
amount: 0
```

浏览器随后只把 close 改成最新价。成交量标签仍为 `11.7K`，而腾讯证券同一时段已经显示约 `12057` 手，证明当前 K 线量能不是实时量能。

### 成功分时图本身的问题

#### 1. 没有均价线

行业常见分时图至少包含价格线和均价线。腾讯证券使用蓝色价格线与橙色均价线，新浪财经使用蓝色价格线与黑色均价线。

项目解析层已经有 `avgPrice`，AKTools parser 甚至会用累计成交额/成交量计算均价，但 `createIntradayChart()` 完全没有创建 average-price series。降级到 `eastmoney-kline-1m` 后 `avgPrice` 全为 0、`amount` 全为 0，也没有补算条件。

#### 2. 涨跌坐标不对称

腾讯和新浪都以昨收为 0% 中轴，上下涨跌幅对称，例如 `+0.64% / -0.64%`。这样相同像素距离代表相同涨跌幅。

项目由 Lightweight Charts 自动缩放，现场上方约 `+0.50%`、下方约 `-0.74%`，不是以昨收对称。价格变化的视觉强度会被扭曲，不能作为规范分时图使用。

#### 3. 坐标标签拥挤并遮挡

项目把“价格 + 百分比”拼进同一个右轴标签，又把 0% 基准线标签和当前价标签放在同一区域。半宽布局下出现：

- `0%`、`1299.56 (0.00%)` 重叠；
- 当前价标签挤进图表与 K 线之间；
- 时间轴首尾文字被裁切成 `:30`、`13:0`；
- 左右两张图的纵轴在中间形成高密度视觉噪声。

行业实现通常是左侧价格轴、右侧涨跌幅轴，或者至少分别对齐，不把两种数值塞进同一个窄标签。

#### 4. 价格线颜色语义不稳定

项目分时价格线固定使用主题的“上涨红色”，即使当前价格低于昨收，整条线仍为红色。国内网站通常使用中性蓝色价格线，再用数值颜色表达涨跌；同花顺默认使用带填充的绿色线，但不会把“上涨色”固定套到所有走势上。

#### 5. 交易时间轴不完整

行业分时图固定展示完整交易日时间框架：`09:30`、`10:30`、`11:30/13:00`、`14:00`、`15:00`，即使下午尚未发生也保留空白区域。腾讯、新浪、同花顺均如此。

项目只对已有 123 个点 `fitContent()`，横轴在当前点结束，没有为下午交易时段预留空间，也没有明确表达午休断点。走势的“当前时刻处于全日什么位置”无法一眼判断。

#### 6. 左右双图缺少针对半宽画布的专门设计

国内站点通常将分时、日 K、周 K、月 K设计为同一主画布的互斥周期。腾讯保留盘口侧栏，同花顺给图表近乎全屏宽度，新浪把盘口放在右侧。

本项目明确要求桌面端固定左右双图，所以不能照搬行业网站改成 tab。实际缺陷是：当前刻度、标签、图例和时间轴仍按宽画布思路直接塞进半宽区域，导致两图可读性不足；需要在保留 `1fr 1fr` 的前提下分别优化双轴、标签密度、图例和响应式策略。分时失败时也必须在左侧画布内提供明确重试与降级状态。

#### 7. 缺少当前点详情与量价联动

项目十字线只记录时间，没有渲染所指分钟的时间、价格、涨跌幅、成交量、均价。腾讯图表顶部明确显示当前指针的价格、涨跌幅、成交量和时间；新浪也显示价、均、量、幅。

#### 8. 分时量柱不实时

分时加载后没有追加新分钟、更新当前分钟价格或当前分钟 volume。成功加载只是一次静态快照；图表标题里的点数和最后时间也一直冻结。

### 图表修复的最低验收标准

1. 当前交易日分时必须每个行情刷新周期更新；同一分钟更新末点，新一分钟追加点。
2. 分时状态中的最后价格与监控表格现价最多相差一个刷新周期，点数随分钟推进。
3. 当前 K 柱必须更新 close、high、low、volume、amount；不能只改 close。
4. 分时主图以昨收为 0%，上下涨跌幅对称；价格轴与百分比轴分离。
5. 增加均价线；若备用数据缺少 amount/avgPrice，必须明确标记“均价不可用”，不能伪造。
6. 横轴固定覆盖 09:30-11:30、13:00-15:00，并明确显示午休断点/压缩规则。
7. 桌面端分时与 K 线保持左右同时展示；K 线周期在右侧画布内切换，成交量使用同步副图；窄屏可上下堆叠。
8. 十字线详情至少显示时间、价、涨跌幅、均价、成交量；K 线显示 OHLC、涨跌幅、MA 和 volume。
9. 数据源 fallback 统一放在服务端，前端不重复瀑布式请求；单个源有独立超时，错误保留 source stage。
10. 增加交易时段 E2E/集成测试：两次行情响应价格不同，断言表格、分时末点、K 线 OHLCV 都同步变化。

### 10 日涨幅扫描（恢复链已完成；外部数据源导致本机终态为 partial）

已完成的恢复链：

1. 新增 `POST /api/cache/momentum/ten-day/scan`，页面“扫描”会真正启动 single-flight 服务端任务；`GET` 只负责状态轮询。
2. AKTools 全市场快照失败且没有成功快照时，使用 `data/cache/kline` 的股票目录恢复 universe；本机共识别 5,863 个代码。
3. 扫描进度写入串行化，轮询读取禁用 `lastAccessedAt` touch，消除 Windows 上 `ten-day-45pct.json.tmp -> ten-day-45pct.json` 的 `EPERM rename` 竞态。
4. 独立保存 `ten-day-45pct-success.json`；新任务失败时保留上次成功项目，不再用空错误结果覆盖。
5. 任务状态带 `jobStartedAt`，GET 不再把前一次任务的扫描计数合并进新任务，进度保持单调。
6. AKTools spot 请求限时 5 秒；K 线优先复用本地缓存，陈旧缓存会强制向东财/腾讯刷新；东财连续失败时短暂熔断并切到腾讯备用。

第一次恢复扫描在仅遍历缓存时于约 52 秒完成 5,863/5,863、命中 27，但人工检查发现其中混入 2001、2014、2021 等退市/陈旧序列。这揭示了第二层正确性 bug：算法把每个缓存文件自己的“最后 10 根”误当成目标日期前 10 个交易日。

随后已修正：计算前按扫描日期截断 K 线，并以全体有效序列中最新交易日作为本次 `latestMarketDate`；最终结果只保留同一最新交易日的数据，同时输出 `freshUniverseSize` 覆盖数。仅使用旧缓存重跑后，结果从 27 降至 5，且最新日覆盖只有 21/5,863，证明不能把“文件遍历完成”冒充“全市场当前扫描完成”。

最终刷新复验中，东财日 K 持续断连，腾讯备用在批量请求后触发 WAF HTTP 501。实现已增加东财失败熔断、腾讯请求限速和 WAF 冷却；熔断期内不再让页面长时间假死，而是完成遍历并记录刷新失败。最终真实结果：

```text

```
