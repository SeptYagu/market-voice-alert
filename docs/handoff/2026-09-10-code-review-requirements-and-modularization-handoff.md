## 已确认缺陷与修改方案

### R1 · P1：周期刷新持续取消慢请求，可能一直没有新行情

位置：`src/js/controllers/monitorController.js:21`、`:24`、`:55`；`src/js/services/requestScope.js`。

每次 interval tick 都调用 refresh，refresh 无条件 scope.begin，begin 会取消上一请求。如果用户选3秒刷新而请求稳定需要4秒，上一请求永远先被下一 tick 取消；即使取消后仍返回，归属校验也拒绝提交。结果为持续 loading/旧价。当前“最新请求拥有状态”的设计适合切换筛选条件，直接用于持续轮询并不适合。

复现 R1：连续4个慢响应全部完成，但均被下一 tick 作废，quotes.size 仍为0。

方案：自动刷新采用完成后再安排下一次的递归 timeout，或 in-flight 时跳过自动 tick；用户显式“立即刷新”才允许替换旧请求。保留 stop、删除、重新启动的归属保护；加整体超时，不能无限等待。验收：请求耗时4秒/间隔3秒仍能持续提交；停止后晚到结果不写状态，手动强刷的新结果不会被旧结果覆盖。

### R2 · P1：行情源全部失败仍被当作刷新成功；部分缺失不补源

位置：`src/js/api.js:131`–`:150`；`src/js/controllers/monitorController.js:30`–`:35`；`src/js/app.js:1150` 附近。

fetchQuotes 把源失败吞成空数组；控制器随后更新时间、执行 onQuotes，并保留旧行情。用户看见新的“更新于”时间，但价格可能没有更新；提醒逻辑仍拿旧 quotes 评估。腾讯只返回部分股票时，只检查 arr.length，缺失代码不会继续请求东财。

复现 R2：所有 fetch 抛错，已有价9被保留，error=null，lastUpdate 更新为本次时刻，onQuotes 仍执行一次。部分缺失路径由 arr.length 分支直接确认，脚本未单独模拟部分批次。

方案：返回带 `quotes/failedCodes/asOf/source` 的结果；按代码对主源缺失项补源；全部失败明确抛出或返回失败状态。将“最后尝试”与“最后有效行情时间”分开，保留旧数据时显示过期状态，自动播报/阈值评估只接受有效且时效合格的数据。AbortError 必须传递，不启动无意义回退。验收覆盖全失败、半成功、请求取消和恢复；失败时成功时间不变，旧行情可见但不伪装成新行情。

### R3 · P2：仅在10日强势股表内的标的没有实时刷新

位置：`src/js/controllers/monitorController.js:13`–`:19`；`src/js/app.js:1400` 附近；`src/js/controllers/momentumController.js:327`。

刷新名单只有 watchList、subscribed 和当日涨停池，没有 momentum.items。后续虽调用 mergeQuotesIntoMomentumItems 和 updateMomentumQuoteCells，但独立强势股没有新报价可用。若它同时在自选或订阅中则不受此遗漏影响。

复现 R3：仅放在 momentum.items 的 sz000001 不在 getRefreshCodes 结果中。

方案：建立页面数据需求汇总函数，把当前需要展示/已展开的强势股加入去重刷新集合，并在扫描结果变更时刷新。仅更新价格不足以证明扫描结果仍符合当天滚动10日窗口；过期扫描的指标应保留扫描日期，并安排指标重算或注明旧基准。验收：只存在于强势股表的股票连续变价能更新，空自选列表同样有效，离开页面时按明确策略保留/移除需求。

### R4 · P1：旧扫描结果覆盖较新报价，形成价格与时间不一致的数据

位置：`src/js/controllers/momentumController.js:134`–`:150`、`:212`；`src/js/services/momentumScanner.js:32`。

_mergeMomentumQuotesSafely 虽保留 existing 的其他字段，却无条件用扫描 item 的 price/changePercent/amount 覆盖实时值。共享扫描可能早于实时刷新，甚至是 stale 返回；既有 time/open 等字段仍保留，形成混合时点的 quote。

复现 R4：现有14:00价格20，扫描价10覆盖后，quote.time 仍为14:00、price变10。该数据还会流向监控、提醒及图表更新。

方案：扫描仅管理扫描结果和领域指标，不写全局实时报价。若确需提供启动占位，只能在实时仓库无记录时放入带 snapshot 标记的数据；统一 quoteStore 按 asOf/来源质量进行整条报价比较与替换，不能只覆盖几个数值字段。验收：先实时后旧扫描、先扫描后实时、过期缓存、置顶历史项等顺序均不倒退。

### R5 · P2：历史涨停池及原因把盘中缓存永久视为完整

位置：`server/limitUpService.js:34`–`:36`、`:67`–`:69`。

只要日期早于今天且存在缓存，就忽略 TTL 返回 stale=false。昨天10:00的涨停池、盘中尚未发布的空龙虎榜原因，第二天打开时不会自动补齐。强制刷新是人工补救，不构成自动归档正确性。股票分时服务已经增加完整性检查，涨停服务未采用同等机制。

复现 R5：写入昨天10:00池和空原因；读取两者均0网络请求、stale=false。

方案：分别定义涨停池与原因发布/归档策略，区分盘中快照、已核验收盘结果、未发布、失败。池需收盘后成功采集才可冻结；原因需要发布后的延迟重试窗口，不能简单复制15:00分时收盘点规则。补齐失败保留缓存并显示日期/时效。验收包含盘中退出次日重开、收盘空池、原因延迟发布、强刷和上游失败。

### R6 · P2：语音队列只限制本地引用，没有限制实际待播内容

位置：`src/js/tts.js:37`–`:60`；`src/js/controllers/voiceController.js:29`–`:37`。

_queue 超50时 shift 仅删除 JS 引用，后续仍每次调用 synth.speak；没有取消已经交给合成器的旧内容，也没有等待上一条完成。高频变价/多订阅时，播报处理不过来会积压过时行情。另外 memory 在调用 speak 后立即更新，并不表示设备真的完成了播报。

复现 R6：注入不自动结束的语音适配器，连续80次调用全部提交到适配器，而声明上限为50。此证据确认缺少应用层背压；未宣称已测得某台真实设备的积压时长。

方案：应用自行维护待播队列，同一时刻只向原生合成器提交一条；onend/onerror 推进，普通行情按 code 合并成最新一条，提醒设优先级及有效期；设备失败/超时清理，区分已入队与已完成记录。验收用延迟结束适配器验证队列上限与最新价合并，再实机听测多标的30分钟、锁屏/恢复及关闭播报。

### R7 · P1：08:00盘前扫描把昨日行情合成为今日K柱，改变10日窗口

位置：`server/momentumService.js:65`–`:86`、`:229`、`:256`。

resolveMomentumScanDates 在当日15:05前一律设置 liveDate=今天，包括配置的08:00扫描。mergeLiveQuoteIntoDailyKline 只看正数 price/open/volume，没有核验报价交易日；盘前刚取得的 HTTP 响应仍可能是昨日 OHLCV。新鲜响应时间不能证明报价属于今天。

复现 R7：09-10 08:00，把明确标为09-09的价20追加为09-10。相同11根历史原本10日涨幅100%，追加重复昨日价后变成81.82%，足以影响阈值筛选。

方案：盘前 marketDate/historyTargetDate 锚定上一完成交易日，liveDate 为空；开盘后仅合成有当天报价时间/交易日证据的数据。无法提供日期的源不得仅凭 HTTP 成功提升为今日成交。验收08:00、开盘前后、停牌及隔夜旧快照；同一交易日的窗口应有10个真实交易间隔，而非10个数组位置加重复日。

### R8 · P1：共享缓存的 stale/生成时间在前端丢失，旧图被显示为正常

位置：`src/js/api.js:456`–`:469`、`:564`；`src/js/limitUpApi.js:189`–`:210`；`src/js/services/momentumScanner.js:32`；`src/js/controllers/chartRowController.js:155`。

多个 API 适配函数仅 return json.data，丢失共享缓存封套的 stale/generatedAt/source。分时状态只显示日期、点数、均价及原数据源，无法识别服务端已经明确标成 stale 的响应。涨停/动量也会把取到旧数据的时间记作这次更新时间。R2 是实时源错误丢失，本项是共享缓存已提供的质量信息丢失。

复现 R8：传入 stale=true、generatedAt=1 的分时封套，经 fetchIntraday 后两字段均为 undefined，formatIntradayStatus 不显示任何缓存/过期提示。线上动量池实际返回 stale=true，证明这一状态不是纯理论分支，但本轮没有把模拟图表错误当作已观测到的线上图表截图。

方案：定义统一结果封套，完整穿过适配层和控制器，明确 dataset.source 与 response.source；所有图表/列表显示 asOf 与过期提示，实时 tick 只能更新可信末点，不能把缺失的历史分时线段伪装成连续交易。验收网络失败缓存兜底、缓存恢复、无数据以及历史完整归档；完整历史数据不应仅因年代久就标为故障。

## 需求是否满足、实现是否合理

| 需求 | 判断 | 依据/限制 |
| --- | --- | --- |
| 自选添加删除、持久化、主题、批量操作 | 基本满足 | 现有单测/E2E通过；没有必要引入前端框架重写 |
| 实时价格、提醒、减少盯盘 | 部分满足 | R1/R2/R4/R8影响可信度；提醒阈值应使用有效行情，不以请求完成时间代替报价时间 |
| 定时播报、交易时段调度 | 主流程具备，负载与实机验收不足 | Worker、会话决策、停用清理合理；R6；Worker本身不构成系统休眠/浏览器冻结下的持续运行保证 |
| 日周月K与历史分时、多行图表 | 主体具备 | 缓存及请求归属是合理设计；腾讯分钟主源本轮实测正常；R8仍会隐藏退化状态 |
| 涨停/炸板分类、原因、历史日期 | 部分满足 | 实时真值来源合理；R5，龙虎榜上榜原因应保留来源标签，不能直接等同于“导致涨停的因果解释” |
| 全市场10日涨幅池 | 部分满足 | 前后端共享数学、服务端扫描、覆盖警告合理；R3/R4/R7，历史不足与抓取失败需区分 |
| 故障可诊断、自用部署维护 | 基本具备 | README一行日志有效，version可比对；公开摘要不能代替原始异常栈，状态文案仍有混淆 |

常识检查的核心不是再换一个数据源，而是“取到数据”与“数据属于哪个时间、是否完整”分开；不应混合旧价格和新时间，不应将盘中缓存天然当收盘归档，不应让几分钟前的待播行情在实时语音中排长队。10日收益用11个有效收盘点计算的公式本身合理，缺陷在输入窗口与日期归属。

## 模块化、精简与实施顺序

### 优先收敛数据责任，不以文件数量作为重构成果

当前已使用纯函数、controllers/views、ChartRowManager、requestScope、服务端 jobRegistry 和通用期货会话。这些应继续保留。单用户 Vanilla JS + Node共享缓存足够，不建议为了重构引入 React/Vue、消息队列、微服务或另一个数据库。

1. **行情领域层**：新增统一 QuoteResult/MarketDataResult 契约、quoteStore、collectQuoteDemand。报价时序、源回退、失效时间、missingCodes 只在此处理；扫描层不能向它写混合报价。先落地 R1/R2/R3/R4/R8。
2. **扫描日期与资格层**：把 resolveScanContext、quoteBelongsToSession、historyEligibility 从扫描编排抽出。区分 insufficientHistory、unavailable、stale、eligible；R7先修。盘中所需历史根数还应结合即将合成的今日柱统一定义，避免各层分别写死11根。
3. **归档策略层**：cacheStore 保持文件存取/TTL职责，业务服务提供 completeness 和 retry 策略；股票分时、涨停池、龙虎榜原因、期货分时各有自己的完整条件。不可让通用缓存把所有非空或历史数据都视为完整。落实 R5。
4. **语音播放层**：tts.js 管原生适配器、单条播放、队列与背压；voiceController 管调度/订阅/开关；voiceSchedule 管纯会话决策。按此边界落实 R6，再做实机验收。
5. **视图增量更新**：涨停视图已能维护节点，动量视图仍在勾选、置顶、轮询 render 时重建，beforeRerenderClean 遍历销毁图表；closeAllMomentumCharts 又逐个 close/render，批量关闭可产生重复重建。复用按code维护行节点与一次性清理模式。此项是性能/维护优化，不能替代前四项正确性修复。

### 可有证据地减少重复
